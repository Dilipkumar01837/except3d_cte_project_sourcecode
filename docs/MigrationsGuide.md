# Migrations Guide

How to create, apply, and roll back Prisma database migrations.

---

## Overview

All schema changes go through Prisma Migrate. The migration history lives in
`database/prisma/migrations/`. Each migration is a timestamped directory containing
a `migration.sql` file generated by Prisma from the diff between the current schema
and the last applied migration.

**Never edit migration SQL files after they have been applied** — Prisma checks the
checksum and will refuse to apply further migrations if a file is modified.

---

## Creating a migration

```bash
# 1. Edit database/prisma/schema.prisma

# 2. Generate and apply the migration (dev only)
pnpm --filter server db:migrate
# Equivalent: prisma migrate dev --name <description>

# Prisma will:
# - Diff the schema against the DB
# - Write a new migration in database/prisma/migrations/
# - Apply it to the local database
# - Regenerate the Prisma client
```

Use a short, descriptive name. Examples:

- `add-user-fcm-token`
- `add-scene-definition`
- `make-world-sort-order-unique`

---

## Applying migrations in production

```bash
# Apply all pending migrations (no interactive prompts, no schema changes)
pnpm --filter server db:deploy
# Equivalent: prisma migrate deploy
```

`migrate deploy` is safe to run on startup in CI or a Docker entrypoint because it:

- Only applies pending migrations (idempotent for already-applied ones)
- Never generates new migrations
- Never drops data without an explicit destructive migration

---

## Seeding content after migration

After applying migrations on a fresh database, seed content in this order:

```bash
pnpm --filter server seed:beginner     # 42 beginner challenges
pnpm --filter server seed:variety      # supplementary challenge types
pnpm --filter server seed:worlds       # 6 worlds + levels + keys + locks
pnpm --filter server seed:achievements # achievements
```

All seed scripts are idempotent — re-running them updates existing rows rather than
duplicating. They are safe to run multiple times.

---

## Resetting the database (development only)

```bash
# Drop everything, re-apply all migrations, re-seed
pnpm --filter server prisma migrate reset
```

**This destroys all data.** Never run on a production or shared database.

---

## Generating the Prisma client

The client is regenerated automatically by `migrate dev` and `migrate deploy`. If you need
to regenerate it manually (e.g. after pulling schema changes):

```bash
pnpm --filter server prisma generate
```

---

## Inspecting migration status

```bash
pnpm --filter server prisma migrate status
```

---

## Rollback

Prisma does not support automatic rollback. To undo a migration:

1. Write a new migration that reverses the change.
2. Apply it with `migrate dev` (dev) or `migrate deploy` (prod).

For destructive changes (dropping a column), create the reversal migration **before** running
the original migration in production if possible.

---

## Schema location

```
database/prisma/
├── schema.prisma      # 48 models — single source of truth
└── migrations/
    └── <timestamp>_<name>/
        └── migration.sql
```

The schema uses a single `datasource db` with `provider = "postgresql"`. The `DATABASE_URL`
environment variable must be set before running any Prisma commands.
